# Kiro2API Python 版 技术架构文档

> 基于 kiro.rs 项目逻辑，使用 Python FastAPI 全异步重写，新增外部 API Key 校验、Admin 站点 API Key 管理及号池分组功能。

---

## 1. 技术栈

| 层级 | 技术选型 | 说明 |
|------|---------|------|
| **语言** | Python 3.12+ | 全程异步 |
| **Web 框架** | FastAPI + uvicorn | 异步 HTTP 服务器 |
| **HTTP 客户端** | httpx (AsyncClient) | 异步请求 + SSE 流式转发 |
| **数据库** | SQLite | 轻量级，零配置，单文件部署 |
| **异步 ORM** | SQLAlchemy 2.0 (async) + aiosqlite | 全异步数据库操作 |
| **数据迁移** | Alembic | 数据库版本管理 |
| **数据验证** | Pydantic v2 | 请求/响应模型验证 |
| **配置管理** | pydantic-settings | .env + 环境变量 |
| **虚拟环境** | uv | 快速依赖管理 |
| **日志** | loguru | 结构化日志 |
| **任务调度** | asyncio (内置) | Token 刷新等后台任务 |

## 2. 功能清单

### 2.1 继承自 kiro.rs 的核心功能

| 功能 | 说明 |
|------|------|
| **Anthropic API 兼容** | 完整支持 Anthropic Claude API 格式（`/v1/messages`、`/v1/models`、`/v1/messages/count_tokens`） |
| **流式响应** | 支持 SSE (Server-Sent Events) 流式输出，Kiro → Anthropic 事件流转换 |
| **Token 自动刷新** | 自动管理和刷新 OAuth Token（支持 Social / IdC 两种认证方式） |
| **多凭据支持** | 支持配置多个凭据，按优先级自动故障转移 |
| **负载均衡** | 支持 `priority`（按优先级）和 `balanced`（均衡分配）两种模式 |
| **智能重试** | 单凭据最多重试 3 次，单请求最多重试 9 次 |
| **凭据回写** | 多凭据格式下自动回写刷新后的 Token |
| **Thinking 模式** | 支持 Claude 的 extended thinking 功能 |
| **工具调用** | 完整支持 function calling / tool use |
| **WebSearch** | 内置 WebSearch 工具 → Kiro MCP 转换逻辑 |
| **多模型支持** | 支持 Sonnet、Opus、Haiku 系列模型映射 |
| **凭据级代理** | 每个凭据可单独配置 HTTP/SOCKS5 代理，优先级：凭据代理 > 全局代理 > 无代理 |
| **Claude Code 兼容端点** | `/cc/v1/messages` 缓冲模式，确保 `input_tokens` 准确 |

### 2.2 新增功能

| 功能 | 说明 |
|------|------|
| **OpenAI 兼容端点** | 新增 `/v1/chat/completions` 端点，自动转换 OpenAI ↔ Anthropic 格式 |
| **外部 API Key 校验** | 外部用户通过独立 API Key 访问服务，与内部 Admin Key 分离 |
| **Admin API Key 管理** | Admin 站点可生成/吊销外部 API Key，并绑定到指定分组 |
| **号池分组管理** | 凭据按分组组织，API Key 绑定分组，请求路由到对应分组的凭据池 |
| **消费记录** | 记录每个外部 API Key 的每次调用：时间、IP、模型、输入/输出 token 数 |
| **Token 额度管理** | 每个外部 API Key 可设置 token 总额度，超额自动拒绝调用 |
| **Kiro 账号状态查看** | 查看每个凭据对应的 Kiro 账号状态（正常/已封禁）、订阅等级、剩余积分/总积分、重置时间 |

| 模式 | 应用位置 | 说明 |
|------|---------|------|
| **依赖注入** | `dependencies.py` | FastAPI `Depends()` 注入 DB session、当前 API Key 信息等 |

| **常量时间比较** | `security.py` | API Key 比较使用 `hmac.compare_digest` 防时序攻击 |

## 5. 核心模块详解

### 5.1 配置管理 (`core/config.py`)

使用 `pydantic-settings` 从 `.env` 文件和环境变量加载配置：

```python
from pydantic_settings import BaseSettings

class Settings(BaseSettings):
    # 服务配置
    HOST: str = "127.0.0.1"
    PORT: int = 8990
    
    # Kiro 配置
    REGION: str = "us-east-1"
    AUTH_REGION: str | None = None      # Token 刷新 Region
    API_REGION: str | None = None       # API 请求 Region
    KIRO_VERSION: str = "0.9.2"
    MACHINE_ID: str | None = None
    NODE_VERSION: str = "22.21.1"
    
    # 认证
    API_KEY: str                        # 内部 API Key（兼容旧模式）
    ADMIN_API_KEY: str | None = None    # Admin 管理 Key
    
    # 代理
    PROXY_URL: str | None = None
    PROXY_USERNAME: str | None = None
    PROXY_PASSWORD: str | None = None
    
    # 负载均衡
    LOAD_BALANCING_MODE: str = "priority"  # priority | balanced
    
    # 数据库
    DATABASE_URL: str = "sqlite+aiosqlite:///data/kiro2api.db"
    
    # count_tokens 外部 API
    COUNT_TOKENS_API_URL: str | None = None
    COUNT_TOKENS_API_KEY: str | None = None
    COUNT_TOKENS_AUTH_TYPE: str = "x-api-key"  # x-api-key | bearer
    
    class Config:
        env_file = ".env"
        env_file_encoding = "utf-8"
```

**Region 优先级**（与 kiro.rs 一致）：
- **Auth Region**（Token 刷新）：`凭据.auth_region` > `凭据.region` > `config.AUTH_REGION` > `config.REGION`
- **API Region**（API 请求）：`凭据.api_region` > `config.API_REGION` > `config.REGION`

```python
    region: Mapped[str | None]
    auth_region: Mapped[str | None]
    api_region: Mapped[str | None]

    subscription_title: Mapped[str | None]
    proxy_url: Mapped[str | None]
    proxy_username: Mapped[str | None]

    # 运行时状态

    failure_count: Mapped[int] = mapped_column(default=0)
    success_count: Mapped[int] = mapped_column(default=0)
```

### 5.3 Token 管理 (`services/token_manager.py`)

移植 kiro.rs 的 `TokenManager` + `MultiTokenManager` 逻辑：

```
MultiTokenManager
├── 管理多个凭据的 Token 生命周期
├── 自动检测 Token 过期（提前 5 分钟）
├── 支持 Social / IdC 两种刷新方式
├── Token 刷新后自动回写数据库
├── 故障转移：当前凭据失败时切换到下一个
├── 提供凭据快照（snapshot）供 Admin API 查询
└── 线程安全：asyncio.Lock 保护并发刷新
```

**Token 刷新流程**：

```
检查 Token 是否过期或即将过期 (5分钟内)
    │
    ├── 未过期 → 直接返回 access_token
    │
    └── 已过期 → 判断 auth_method
         ├── social → POST https://oidc.{auth_region}.amazonaws.com/token
         │            grant_type=refresh_token
         │
         └── idc → POST https://oidc.{auth_region}.amazonaws.com/token
                   grant_type=refresh_token + client_id + client_secret
         │
         └── 刷新成功 → 更新 access_token / expires_at → 回写数据库
```

### 5.4 Kiro Provider (`services/kiro_provider.py`)

移植 kiro.rs 的 `KiroProvider`，核心职责：

```
KiroProvider
├── 构建 Kiro API 请求（generateAssistantResponse）
├── 设置请求头（Authorization, x-amz-*, User-Agent 等）
├── 管理 httpx.AsyncClient 实例（按代理配置缓存）
├── 多凭据故障转移 + 重试逻辑
│   ├── 单凭据最多重试 MAX_RETRIES_PER_CREDENTIAL = 3 次
│   ├── 总重试上限 MAX_TOTAL_RETRIES = 9 次
│   └── 重试间隔指数退避
└── 解析 AWS Event Stream 响应
```

**请求路由流程（新增分组）**：

```
外部请求 (带 API Key)
    │
    ├── 查询 API Key → 获取绑定的 group_id
    │
    ├── 在该 group 的凭据池中按负载均衡模式选号
    │   ├── priority: 按优先级从小到大，选第一个可用凭据
    │   └── balanced: 在可用凭据中均衡分配
    │
    └── 调用 Kiro API（含故障转移）
         ├── 成功 → success_count++, 更新 last_used_at
         └── 失败 → failure_count++, 切换下一个凭据重试
```

### 5.4.1 Kiro 账号状态与积分查看

参考 `kiro-account-manager` 项目（`codewhisperer_client.rs`、`account_cmd.rs`），通过上游 `getUsageLimits` API 获取账号的完整状态信息。

**上游 API**：

```
GET https://codewhisperer.us-east-1.amazonaws.com/getUsageLimits
    ?isEmailRequired=true&origin=AI_EDITOR&resourceType=AGENTIC_REQUEST
Authorization: Bearer <access_token>
```

**响应数据结构**（缓存到 `credentials.usage_data`）：

```python
class UsageLimitsResponse(BaseModel):
    days_until_reset: int | None
    next_date_reset: float | None                # Unix 时间戳
    user_info: UserInfo | None                    # email, user_id
    subscription_info: SubscriptionInfo | None    # subscription_title, type, overage_capability
    usage_breakdown_list: list[UsageBreakdown]    # 积分明细列表
    overage_configuration: OverageConfiguration | None

class UsageBreakdown(BaseModel):
    usage_limit: int | None                       # 总积分
    current_usage: int | None                     # 已用积分
    usage_limit_with_precision: float | None      # 总积分（高精度）
    current_usage_with_precision: float | None    # 已用积分（高精度）
    next_date_reset: float | None                 # 重置时间
    display_name: str | None                      # "Agentic Request" 等
    resource_type: str | None                     # 资源类型
    free_trial_info: FreeTrialInfo | None         # 免费试用信息
    bonuses: list[BonusInfo] | None               # 奖励积分
```

```json
      "remaining": 650,
      "usagePercentage": 35.0,
      "nextDateReset": 1740000000.0
    }
  ],
  "daysUntilReset": 12,
  "updatedAt": "2025-02-18T12:00:00Z"

```

**账号状态检测流程**：

```
Token 刷新成功后 / Admin 手动查询
    │
    ├── 调用 getUsageLimits API
    │
    ├── 成功 → 解析响应
    │   ├── 提取 email, subscription_title
    │   ├── 提取 usage_breakdown_list → 计算剩余积分/总积分
    │   ├── account_status = "normal"
    │   └── 缓存 usage_data JSON + usage_data_updated_at
    │
    └── 失败
        ├── BANNED:* 错误 → account_status = "banned"
        │   └── 自动禁用凭据 (disabled = true)
        └── 其他错误 → 保留旧数据，记录日志
```

**订阅等级与模型过滤**（移植自 kiro.rs）：
- `KIRO FREE`：不允许使用 Opus 系列模型
- `KIRO PRO+`：允许所有模型
- 添加凭据后主动获取订阅等级，避免首次请求时 Free 账号绕过 Opus 过滤

### 5.5 协议转换 (`services/converter.py`)

移植 kiro.rs 的 `converter.rs`，负责 Anthropic → Kiro 格式转换：

| 转换项 | Anthropic 格式 | Kiro 格式 |
|--------|---------------|-----------|
| **模型映射** | `*sonnet*` → `claude-sonnet-4.5`<br>`*opus*` (4.5) → `claude-opus-4.5`<br>`*opus*` (其他) → `claude-opus-4.6`<br>`*haiku*` → `claude-haiku-4.5` | Kiro 内部模型 ID |
| **消息结构** | `messages: [{role, content}]` | `conversationState` 嵌套结构 |
| **系统提示** | `system: str \| [{text}]` | `userInputMessage.userInputMessageContext` |
| **工具定义** | `tools: [{name, description, input_schema}]` | `toolSpecifications: [{toolName, description, inputSchema}]` |
| **工具结果** | `content: [{type: "tool_result", ...}]` | `toolResults: [{...}]` |
| **Thinking** | `thinking: {type, budget_tokens}` | 请求参数中的 thinking 配置 |
| **图片** | `source: {type: "base64", ...}` | Kiro 图片格式 |

### 5.6 流式响应处理 (`services/stream.py`)

移植 kiro.rs 的 `stream.rs`，实现 Kiro → Anthropic SSE 事件流转换：

```
Kiro AWS Event Stream
    │
    ├── 解析二进制帧 (header + payload + CRC)
    │
    ├── 提取事件类型
    │   ├── assistantResponseEvent  → 文本/thinking 内容
    │   ├── contextUsageEvent       → Token 使用统计
    │   ├── supplementaryWebSearchEvent → WebSearch 结果
    │   └── 错误事件
    │
    └── 转换为 Anthropic SSE 格式
        ├── event: message_start     (含 message id, model, usage)
        ├── event: content_block_start
        ├── event: content_block_delta (text/thinking/tool_use 增量)
        ├── event: content_block_stop
        ├── event: message_delta     (stop_reason, usage)
        └── event: message_stop
```

**Thinking 标签处理**：
- 检测 `<thinking>` / `</thinking>` 标签边界
- 跳过被引用字符包裹的假标签（反引号、引号等）
- 只识别后跟 `\n\n` 的真正结束标签

**Claude Code 缓冲模式** (`/cc/v1/messages`)：
- 完整接收上游流，等待 `contextUsageEvent`
- 用准确的 `input_tokens` 修正 `message_start` 事件
- 一次性返回所有事件，等待期间每 25 秒发送 `ping` 保活

### 5.7 WebSearch 处理 (`services/websearch.py`)

移植 kiro.rs 的 `websearch.rs`：

```
Anthropic WebSearch 请求
    │ tools 列表仅含一个 web_search 类型工具
    │
    ├── 提取搜索查询
    │
    ├── 构建 Kiro MCP 请求 (JSON-RPC 2.0)
    │   POST https://q.{region}.amazonaws.com/mcp
    │
    ├── 解析 MCP 响应
    │
    └── 转换为 Anthropic 格式
        ├── tool_use content block (搜索调用)
        └── 搜索结果嵌入响应
```

### 6.1 Anthropic 兼容端点

| 路径 | 方法 | 认证 | 说明 |
|------|------|------|------|
| `/v1/models` | GET | API Key | 获取可用模型列表 |

> **`/v1/messages` 与 `/cc/v1/messages` 的核心区别**：
>
> | 对比项 | `/v1/messages` | `/cc/v1/messages` |
> |--------|---------------|-------------------|
> | **流式行为** | 实时流式返回，`message_start` 中的 `input_tokens` 是**估算值** | **缓冲模式**：等待上游流完全结束后，用 `contextUsageEvent` 计算**准确的** `input_tokens`，修正 `message_start`，然后一次性返回所有 SSE 事件 |

> | **非流式** | 逻辑完全相同 | 逻辑完全相同（均使用 `contextUsageEvent` 的准确值） |
> | **适用场景** | 通用 API 客户端 | Claude Code 等需要精确 token 统计的客户端 |

**认证方式**（与 kiro.rs 一致）：
- `x-api-key: <key>` header

## 8. 号池分组与请求路由

### 8.1 分组模型

```
Group A (默认分组)
├── Credential #1 (priority=0, social)
├── Credential #2 (priority=1, idc)
└── Credential #3 (priority=2, social)

Group B (高级分组)
├── Credential #4 (priority=0, social)
└── Credential #5 (priority=1, idc)

API Key sk-ext-aaa → Group A
API Key sk-ext-bbb → Group B
```

### 8.2 请求路由流程

```
POST /v1/messages (API Key: sk-ext-aaa)
    │
    ├── Auth 中间件：校验 sk-ext-aaa → group_id = A
    │
    ├── 在 Group A 的凭据池中选号
    │   ├── 过滤掉 disabled=True 的凭据
    │   ├── priority 模式：按 priority 升序，选第一个可用
    │   └── balanced 模式：按 success_count 升序，选最少使用的
    │
    ├── Converter：Anthropic → Kiro 格式转换
    │
    ├── KiroProvider：调用 Kiro API
    │   ├── 成功 → Stream 响应
    │   └── 失败 → 故障转移到 Group A 的下一个凭据
    │
    ├── Stream：Kiro → Anthropic SSE 转换后返回客户端
    │
    └── 响应完成后异步写入消费记录
        ├── 记录: api_key_id, timestamp, client_ip, model, input/output tokens
        └── 累加: api_keys.tokens_used += total_tokens
```

## 10. 应用生命周期

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    """应用生命周期管理"""
    # ===== 启动阶段 =====
    # 1. 加载配置
    settings = get_settings()
    
    # 2. 初始化数据库连接 + 自动建表
    await init_database()
    
    # 3. 从数据库加载凭据，初始化 MultiTokenManager
    token_manager = await MultiTokenManager.from_database()
    
    # 4. 创建 KiroProvider
    kiro_provider = KiroProvider(token_manager, proxy_config)
    
    # 5. 启动后台 Token 刷新任务
    refresh_task = asyncio.create_task(token_manager.background_refresh_loop())
    
    # 6. 初始化 count_tokens 配置
    init_count_tokens_config(settings)
    
    yield  # 应用运行中
    
    # ===== 关闭阶段 =====
    # 1. 取消后台任务
    refresh_task.cancel()
    
    # 2. 关闭 httpx 客户端
    await kiro_provider.close()
    
    # 3. 关闭数据库连接
    await close_database()
```

## 15. 关键实现注意事项

1. **异步一致性**：所有 I/O 操作（数据库、HTTP 请求、文件操作）必须使用 async/await，避免阻塞事件循环
2. **Token 并发刷新**：使用 `asyncio.Lock` 确保同一凭据不会并发刷新，与 kiro.rs 的 `TokioMutex` 对应
3. **API Key 安全存储**：数据库只存 SHA-256 哈希，生成时一次性返回明文，后续不可查看
4. **常量时间比较**：API Key 校验使用 `hmac.compare_digest()` 防止时序攻击，对应 kiro.rs 的 `subtle::ConstantTimeEq`
5. **SSE 流中断处理**：客户端断开时及时清理上游连接，避免资源泄漏
6. **Thinking 标签检测**：移植 kiro.rs 的 `find_real_thinking_end_tag` 逻辑，正确处理被引号包裹的假标签
7. **Write/Edit 工具截断策略**：移植 `WRITE_TOOL_DESCRIPTION_SUFFIX` 和 `EDIT_TOOL_DESCRIPTION_SUFFIX`，防止输出过长导致会话卡死
8. **凭据级代理**：每个凭据可独立配置代理，`direct` 表示显式直连；httpx AsyncClient 按代理配置缓存复用
9. **余额缓存**：余额查询结果缓存 5 分钟（与 kiro.rs 的 `BALANCE_CACHE_TTL_SECS = 300` 一致），避免频繁请求上游
10. **分组隔离**：不同分组的凭据池完全隔离，故障转移只在同一分组内进行
11. **消费记录异步写入**：调用完成后异步写入 `usage_logs` 表，不阻塞响应返回
12. **额度检查前置**：请求到达时先查 `tokens_used` vs `token_quota`，超额直接返回 429 Too Many Requests，粗略判断即可（不需等实际完成）
13. **账号状态检测**：通过上游 `getUsageLimits` API 检测账号状态，若返回 `BANNED:*` 错误则标记为已封禁并自动禁用该凭据
14. **积分数据缓存**：`usage_data` 缓存上游响应原始 JSON，避免频繁请求；Admin API 查询时可强制刷新
